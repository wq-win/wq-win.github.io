087｜SWE-agent：模型不会稳定修代码，问题可能也在工具接口

返回目录 · 发展时间线

论文：John Yang、Carlos E. Jimenez 等，SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering，2024。依据原文 v3的接口设计、主实验、消融与行为分析附录；代码及配置见官方项目。实验对应文中模型快照和当时 API 价格，不能作为当前产品性能或报价。

一分钟理解：给模型一套合适的工作台

给语言模型一个终端，它理论上就能搜索文件、修改代码、运行测试。但一次多行替换可能需要复杂转义；搜索可能输出几千行；修改失败后文件是否改变也不清楚。模型的失败未必都来自不懂程序，也可能来自无法可靠地操作工具。

SWE-agent 在固定语言模型外设计 Agent-Computer Interface，简称 ACI：用简洁的搜索命令、带行号的文件窗口、带语法检查的编辑操作，以及压缩旧观察的历史管理，组织“观察—思考—执行”循环。

表 1 中，GPT-4 Turbo 在 SWE-bench Lite 上使用这套接口解决 18% 的问题，使用带示范的 Shell-only 接口解决 11%。差异为 7 个百分点，约 63.6% 相对提升。模型权重没有改变；改善发生在交互系统层面。

一句话：在仓库级软件修复中，通过面向语言模型的操作与反馈接口，提高有限预算内产生有效补丁的概率，代价是多轮推理费用、接口工程，以及仍然有限的错误恢复能力。

五个前置概念

五个前置概念：ACI定义代理可做什么与能看到什么；ReAct交替生成推理、行动与观察；补丁表示仓库前后差异；回归测试检查既有行为未受破坏；Pass@K统计 K 次尝试中至少一次成功，区别于自动选出正确结果。

背景：代码问答与实际修复之间差了什么

任务输入是仓库的某个历史状态和一条问题描述，输出是补丁。代理不知道正确修改在哪里，需要定位、理解、修改、验证；最终由独立测试判断修复是否有效。这是交互式软件环境中的单代理推理，论文没有通过在线 RL 更新模型参数。

可以借用强化学习语言描述：仓库和执行环境构成状态，代理看到的只是部分文件及命令反馈，动作包括搜索、编辑和执行，终止来自主动提交或预算耗尽。但终局测试得分是评估指标，不是这篇论文用于训练策略的奖励信号。

与 SWE-bench 原始 RAG 基线相比，代理能够主动改变工作目录里的代码并得到执行反馈。与 Shell-only 相比，关键差异是怎么表达操作，以及操作后返回什么。它保留普通 shell 作为底层能力，新增的动作不是把计算机功能重新实现一遍，而是提供更易组合的语义操作。

方法：接口同时决定动作空间和观察空间

搜索：先给全局摘要，再局部阅读

find_file 搜索文件名，search_dir 与 search_file 搜索内容。结果控制在 50 条以内，超过时要求缩小查询，而不是截取最前面的若干条假装已经全面呈现。

这个细节改变代理行为：如果只提供“下一条匹配”，模型可能不断翻页，直到预算耗尽。摘要式结果让它先比较候选位置，再决定读哪个文件。它仍可能遗漏正确结果，但减少了机械遍历的交互成本。

阅读与编辑：共享行号和即时状态

文件查看器一次呈现最多 100 行，并附路径、总行数、上下文省略范围和每行行号。goto 与滚动命令改变窗口；edit 接收起止行和替换文本，与查看器共享坐标。

编辑完成后自动显示新内容。对选定的严重 lint 错误，系统拒绝变更，展示错误及前后片段，要求重试。这里检查的是语法等局部约束，不能证明业务逻辑正确。成功通过 lint 只是允许后续执行测试的最低门槛。

历史：保留决策轨迹，压缩陈旧观察

模型每轮输出思考和命令。格式错误会收到明确反馈；命令成功但没有标准输出时也给出说明。超过最近五条的环境观察被折叠，避免旧版本代码持续占据上下文。

这不等于删除所有历史。代理仍需要知道做过哪些操作及为什么做。压缩观察可能丢掉后续有用信息，因此设计必须在陈旧内容与可追溯性之间取舍。

结果与消融：接口为什么值得单独研究

证据一：表 1，交互及 ACI 均有增益。 GPT-4 Turbo 的全 SWE-bench 成绩为 286/2294，即 12.47%；其 RAG 基线为 1.31%。但两者计算和反馈不同。Lite 上 ACI 18% 对带示范 Shell-only 11% 才更直接体现接口改进。若与不带示范的 Shell 7.33% 比，会得到 10.67 个百分点，必须注明示范也发生了变化。

证据二：表 3，编辑与即时校验降低无效操作。 完整系统 18%，保留编辑但移除 lint 为 15%，移除专用编辑为 10.3%。这支持整合式编辑与错误拦截有价值。它不能证明 lint 会发现语义错误，也不意味着所有编程语言都具有同样的检查器收益。

证据三：表 3，更多信息和更多操作并非总是更好。 100 行窗口为 18%，30 行为 14.3%，整文件为 12.7%；摘要式搜索为 18%，逐条搜索为 12%，不提供专用搜索为 15.7%。机制解释是信息粒度影响定位和预算，但这些数字仅验证被测模型与任务，并非“100 行永远最优”的定律。

证据四：表 10 与图 4，多次尝试扩大覆盖。 六次独立运行的单次成功率均值为 17.94%，表中离散量为 0.49；Pass@6 达 32.67%。这表示六条轨迹中存在成功补丁的比例上升，不代表系统已有一个无成本、准确选择成功补丁的方法。

证据五：§5.2 与附录 B.4，错误恢复仍是瓶颈。 全集 51.7% 轨迹至少经历一次失败编辑。未解决实例中，自动分类约 52% 属于实现错误或过于特定的实现，23.4% 属于编辑恢复失败。这些类别由模型自动标注，应当作为行为分析线索，而非人工核验的精确因果分解。

表 2 的 HumanEvalFix 成绩分别是 Python 87.7%、JS 89.7%、Java 87.9%；其约 88.3% 的跨语言平均值与 Python 单项要分开。单文件中无需大规模定位，所以高分不抵消仓库级任务的低成功率。

贡献、代价与局限

这篇论文把提示、工具文档、动作粒度、反馈和历史管理当作一个共同设计对象。它没有提出新的 Transformer，也没有以更大训练集解释全部差异。贡献在于固定模型条件下，接口可以成为可实验、可消融的能力来源。

费用是实质代价。Lite 成功实例的平均费用为 1.67 美元，而同模型 RAG 为 0.13 美元；不能只展示成功率倍数而隐藏交互成本。预算受价格影响，不同模型用相同美元并不表示拥有相同 token 或思考轮数。

作者观察到成功任务往往较快结束，失败任务拖得更久。这是相关关系：困难任务导致更长轨迹，不能据此推断“强制早停会提升成功率”。安全地利用这个规律需要验证可在线识别的失败信号及重新开始策略。

接口还有适用边界。基于行号的编辑在并行变更和陈旧观察下会错位；严格 lint 有时会阻止合理的多步重构中间状态；只保留最近观察可能丢失跨文件依赖。以上是从机制推得的工程边界，原文没有完整测试所有这些场景。

一个自构例子与五个前置概念

假设问题是空列表输入导致统计函数异常。代理先搜索函数名，在 100 行窗口内看到 total / len(values)，添加空列表分支，随后自动看到新代码。若缩进错误，编辑被拒绝并指出行号，原文件保持可执行；若缩进正确但返回类型错误，lint 不会解决问题，需要运行正常输入和空输入测试。

这个例子说明三层不同责任：接口保证编辑可表达，检查器拦截局部错误，测试检验行为。任何一层都无法代替完整需求理解。

自测：能否从系统结果推回实验结论

1. 不更新模型参数，为什么解决率仍会改变？

模型根据上下文选择动作。接口改变可选操作、动作执行可靠性和返回的信息，因此改变下一步输入和整条轨迹。例如一次可靠的多行编辑替代五次易错 shell 操作，能让相同模型在相同预算下更早得到测试反馈。这里提升的是闭环系统能力，不是模型权重中的知识量。

2. 18% 与 7.33% 能否直接作为纯 ACI 增益？

不能完全这样解释。7.33% 是没有示范的 Shell-only；带示范版本为 11%。更接近接口效应的直接比较是 18% 对 11%，同时还要核对预算与配置选择。若引用 10.67 个百分点，应承认示范条件也不同。

3. Pass@6 为 32.67%，是否表示给用户运行六次就能可靠得到同样成功率？

它表示六次中至少存在一个通过基准评估的补丁。实际系统还需决定选择哪个补丁，且不能访问泄漏答案的测试；六次费用和延迟也必须计入。只有配套可靠验证与选择机制，候选覆盖才能转化为可交付成功率。
